我把这 9 篇文章放在一起看了一遍。我的初步判断是：如果你的目标是发一篇 CCFA 认可的系统方向论文，我不建议再从 Expert Placement、Expert Prefetching、Expert Caching 或 Expert Scheduling 本身寻找小幅改进。

这些方向已经形成了比较明显的研究脉络。更值得做的是：找到 MoE 推理系统中一个被现有工作简化处理的环节，证明它在真实边缘场景中会成为新的性能瓶颈，再设计一个跨模块的协同优化机制。

我目前最看好的方向是：

首选研究方向

Joint KV Cache and Expert Cache Management for Edge MoE Serving

面向动态上下文和多请求负载的 KV Cache–Expert Cache 协同管理。

核心问题：

现有系统通常将 Expert Weights 和 KV Cache 当作两类相对独立的资源管理，但在内存受限的边缘设备上，它们实际上竞争同一套 DRAM/VRAM、内存带宽和 I/O 通道。

当上下文变长、并发请求增加时，KV Cache 会挤占 Expert Cache 的空间，导致专家频繁换入换出；而专家加载又会与 Attention 的 KV 访问争夺带宽。

真正应该优化的不是专家权重放在哪里，而是整个推理过程中，有限的内存和带宽应该在 KV Cache、Expert Weights、Activation 之间如何动态分配。

这个方向并不是凭空想出来的。尤其值得注意的是，Saber 在论文中明确认为，KV Cache 在典型边缘场景中很少成为瓶颈，因为其假设边缘请求通常具有较短的输入序列。这恰好是一个可以重新审视的系统假设。

但我先强调：这是一个有依据的研究假设，不代表已经证明现有文献完全没有研究过 KV Cache 与 Expert Cache 的联合管理。下面我会具体分析论文的覆盖范围、真正的研究空白，以及如何把这个 idea 做成一篇有竞争力的论文。

## 二、为什么我选择 KV Cache–Expert Cache 这个方向？

这里需要认真处理已有工作的重叠问题。

我专门对照了四篇最相关的文章。

1. Saber：最值得关注的一个研究假设

Saber 是这组文章中最接近你要做的在线边缘推理系统的工作。

它通过相似的 expert activation paths 对请求进行分组，解决多个请求合并后激活专家数量大幅增长的问题。

但它在 KV Cache Management 部分明确指出：

- 默认将 KV Cache 存储在 GPU Memory。
- 内存限制严格时才将其 offload 到 CPU。
- 其设计依据是边缘应用通常使用较短输入序列，因此 KV Cache 很少成为瓶颈。
- 对长序列可以考虑 Sparse Attention 和 PagedAttention。

MOBICOM26-Sparsity-Aware Scheduling for Efficient MoE-Based LLM Serving on Edge Servers.pdf

这段内容非常值得研究。

它相当于给后续研究设定了一个条件：边缘请求的上下文通常比较短。

但如果考虑以下应用：

- Edge RAG：用户上传大量本地文档进行检索问答。
- 多轮私人助手：历史对话不断累积。
- Edge Code Assistant：需要较长代码上下文。
- 本地知识库问答：输入可能包含大量检索结果。

这个假设就未必成立了。

于是可以提出一个问题：

当 KV Cache 不再可以忽略时，Saber 这种以 Expert Activation Similarity 为主要依据的调度机制还是否最优？

这是非常好的切入点。

2. Klotski：不能忽略的最接近工作

需要特别注意，Klotski 已经不是完全忽略 KV Cache 的论文。

它的设计包括：

- Adaptive Tensor Placement：将 Expert、Attention、KV Cache、Activation 等不同 Tensor 放在不同存储层级。
- 四个 CUDA Streams：分别负责权重预取、专家权重传输、KV Cache 预取和 KV Cache 写入。
- 使用 Sparse Attention 减少 KV Cache 大小。
- 通过多 Batch Pipeline 平衡 KV Cache 开销与计算/I/O 重叠。

ASPLOS25-Klotski Efficient Mixture-of-Expert Inference via Expert-Aware Multi-Batch Pipeline'.pdf

因此，不能简单把论文创新点写成：

> We are the first to jointly consider KV Cache and Expert Cache.

这个表述很容易被 Klotski 反驳。

但 Klotski 的重点是多 Batch Pipeline 和吞吐优化。它根据当前硬件测量、计算与传输时间确定批处理参数，并没有把重点放在在线多用户请求的动态 KV 增长、请求准入和长期服务状态管理上。

这里才有进一步研究的空间。

3. MoE-Lightning：已经注意到 KV Cache 与系统资源的关系

MoE-Lightning 在 Prefill 阶段将 Attention 放在 CPU 上，并把 KV Cache 放到 CPU Memory；在 Decode 阶段通过 CGOPipe 协同 CPU、GPU 和 I/O。

它的 HRM 性能模型也考虑了 CPU Memory、GPU Memory 和 CPU-GPU 带宽。

更加重要的是，它在 Future Work 中明确提出：

- 将 KV Cache Sparsity 纳入性能模型。
- 在 CPU Attention 成为瓶颈时，调整 KV Cache Budget，以平衡 CPU 和 GPU 的计算。
- 扩展 Disk Offloading 能力。

ASPLOS25-MoE-Lightning High-Throughput MoE Inference on Memory-constrained GPUs.pdf

这说明 KV Cache 与异构资源的协同确实是一个值得继续研究的问题。

但 MoE-Lightning 的核心定位是 GPU 受限环境下的吞吐优化，而不是长上下文、多请求、动态到达的边缘在线服务。

4. CFMoE：边缘内存架构提供了很好的研究基础

CFMoE 有一个很好的背景：边缘 SoC 往往采用 Unified Memory Architecture，CPU、GPU、NPU 共享有限的 DRAM，剩余专家权重放在 Flash 中。

它主要解决的是 Expert Routing Locality，以及 Prefill/Decode 阶段不同的 Expert Cache Layout。

MOBICOM26-CFMoE Cache-Friendly Mixture of Experts Model Serving System on Edge Devices.pdf



但它的专家缓存管理与 KV Cache 的动态增长并没有形成一个统一的在线资源决策机制。

这给我们的研究提供了一个很自然的出发点。

## 三、真正值得研究的核心：KV–Expert Interference Loop

我认为这个问题可以进一步提炼成一个比简单的 Cache Management 更有研究价值的系统现象。

核心研究假设

KV Cache 和 Expert Cache 的资源竞争会形成一个正反馈循环，最终导致边缘 MoE Serving 的性能崩溃。

具体来看：

1. KV Cache 持续增长

长上下文、多轮对话和并发请求使 KV 占用不断增加。

2. Expert Cache 可用空间减少

原本可以驻留在快速内存中的热点专家被迫换出。

3. Expert Cache Miss 增加

专家需要重新从 DRAM 或 Flash 加载，产生额外 I/O。

4. Decode Latency 增加

Expert Loading 与 Attention 的 KV 访问进一步争夺内存带宽。

5. 活跃请求生命周期变长

在固定请求到达率下，平均服务时间增加会导致更多请求同时处于执行状态。

返回步骤 1：进一步增加 KV Cache 总占用

这个循环背后的重要关系是 Little's Law：

\[ N \approx \lambda W \]

其中：

- \(N\)：系统中的平均活跃请求数。
- \(\lambda\)：请求到达率。
- \(W\)：平均服务时间。

当 Expert Cache Miss 让请求执行变慢时，系统中同时运行的请求数量可能进一步增加，导致 KV Cache 总占用继续上升。

这里有一个非常值得验证的假设：

系统可能存在一个 KV Cache 占用或请求到达率的临界点，超过这个临界点后，Expert Cache Hit Rate 和 TPOT 会出现非线性恶化。

这比简单地说「KV Cache 占用太大」更有研究价值，因为它揭示了一个跨阶段的系统反馈机制。

当然，这个正反馈循环目前是我们的研究假设，需要通过实验验证，不能直接当成已经被论文证明的结论。

## 四、如何将它设计成一篇完整的系统论文？

我建议不要把它做成单纯的 KV Cache 管理算法，而是做成一个 Online, KV-Growth-Aware MoE Serving System。

暂时可以给它取名：

# KVE-MoE

Joint KV Cache and Expert Memory Orchestration for Online Edge MoE Serving

### 4.1 系统模型

考虑一个边缘服务器，包含：

- GPU/NPU：执行 Attention 和 Expert Computation。
- DRAM：存储部分 Expert Weights、KV Cache 和 Activation。
- Flash/SSD：存储尚未加载的 Expert Weights，以及可 offload 的状态。
- 多个 Edge Clients：持续发送不同长度、不同任务类型的请求。

系统需要同时管理三种资源：

\[ M_{\text{fast}} = M_{\text{KV}}+ M_{\text{Expert}}+ M_{\text{Activation}}+ M_{\text{Runtime}} \]

并且需要考虑共享带宽：

\[ B_{\text{shared}} = B_{\text{KV}}+ B_{\text{Expert-I/O}}+ B_{\text{Activation}} \]

这里最关键的是：这两个约束都不是静态的。

Expert Working Set 随着请求的 Router 输出而变化，KV Cache 则随着请求的生成过程持续增长。

### 4.2 三个核心设计模块

Module 1：Future-aware KV Growth Predictor

预测层

不只统计当前 KV Cache 使用量，还要预测未来一段时间的 KV 增长。

对于请求 \(r\)，可以根据：

- 当前 Prompt Length。
- 当前 Decode Length。
- 最大生成长度或预计剩余生成长度。
- Attention Heads、KV Heads、Hidden Dimension。
- KV Cache Precision。

估计未来 KV Cache 占用：

\[ \widehat M^{KV}_r(t+\Delta) = M^{KV}_r(t)+\Delta \cdot \widehat g_r \]

其中 \(\widehat g_r\) 表示预测的 KV 增长速率。

这样系统可以提前知道：接下来某个请求会不会挤占 Expert Cache，而不是等到 OOM 或 Cache Miss 出现才做调整。

Module 2：Joint KV-Expert Memory Manager

内存管理层

这是整篇论文的核心。

动态决定有限的快速内存应该分配给：

- 哪些 KV Pages？
- 哪些 Hot Experts？
- 哪些 Expert 应该被移到 DRAM/Flash？
- 哪些 KV 数据可以进行低比特量化或分层存储？

关键不是给 KV 和 Expert 分别设计两个独立的 LRU，而是计算不同数据驻留在快速内存中所能节省的延迟。

例如：

当 KV Cache 即将增长到较高水位时，系统可以适当减少低复用率专家的驻留空间；当 KV 负载下降时，再将更多空间分配给高复用率专家。

可以进一步设计一个 latency-saving-per-byte 的资源价值函数，综合考虑访问频率、数据大小和重新加载代价。

特别注意：Full Attention 下不能简单把历史 KV 当作不再使用的数据进行 LRU 淘汰。需要结合 Attention 类型选择分层存储、KV 量化或支持的稀疏注意力策略。

Module 3：KV-Expert-Aware Online Scheduler

调度层

在 Saber 的基础上进一步优化请求分组和准入。

Saber 主要根据 Expert Activation Path Similarity 组织 Batch。

我们则同时考虑：

1. Expert Activation Similarity。
2. 当前 KV Cache Size。
3. 未来 KV Cache Growth。
4. 请求的剩余 SLO Budget。

例如，两个请求的 Expert Activation Path 非常相似，但一个请求有 512 tokens 的上下文，另一个有 16K tokens 的上下文。

单纯从 Expert 的角度看，把它们放进同一个 Batch 很合理；但考虑未来 KV 增长之后，这可能不是最优选择。

Scheduler 可以根据预测的联合内存占用决定：

- 是否合并 Batch。
- 是否拆分 Prefill。
- 是否延迟某个请求的准入。
- 是否优先执行即将违反 SLO 的请求。
- 是否推迟不在当前关键路径上的 Expert Prefetch。

最终实现 Expert Sparsity、KV Memory 和 Request Latency 的联合优化。

我认为三个模块中，Module 2 + Module 3 是论文的主要创新，Module 1 是支撑它们的关键机制。

这样做的好处是：不是简单地把两个已有 Cache Policy 拼起来，而是通过预测、内存分配、在线调度形成一个闭环系统。

## 六、这个 Idea 与已有工作的创新边界

这是我认为最需要注意的地方。

不能把论文写成：

> Existing MoE systems ignore KV Cache, and we propose joint KV and Expert Cache management.

因为这个论断不成立。Klotski 和 MoE-Lightning 都已经考虑了 KV Cache。

我建议把创新点严格限定为：

| 维度         | 已有工作                                 | 你的研究                            |
| ------------ | ---------------------------------------- | ----------------------------------- |
| KV Cache     | 独立处理或作为 Tensor Placement 的一部分 | 与 Expert Working Set 联合决策      |
| Expert Cache | 根据路由、冷热程度管理                   | 根据未来 KV 增长动态调整预算        |
| Workload     | 短请求或 Batch-oriented 工作负载较多     | 长短混合、动态到达的在线请求        |
| Scheduling   | 主要考虑专家相似性、计算/I/O 重叠        | 同时考虑专家路径、KV 增长和请求 SLO |
| Optimization | 局部优化                                 | 处理跨阶段的内存与带宽反馈          |

真正的创新不是 Joint Cache 这四个字，而是 KV Growth 如何改变 Expert Working Set，以及这种变化如何进一步影响在线请求调度。

这才是你的论文应该讲的故事。

## 七、另外两个值得保留的 Idea

虽然我目前最推荐上面的方向，但从这九篇文章中，还可以挖掘两个不同的研究机会。

备选方向 1

Mobility-aware KV Cache Migration for Distributed Edge MoE

研究场景：用户在不同 Edge Servers 之间移动。

现有 DIRECTOR 研究的是 Expert 在 GPU 节点之间的动态放置和迁移。

但一个正在生成的 LLM 请求，不仅需要专家权重，还需要其历史 KV Cache。

当用户从 Edge Server A 移动到 B 时：

- 是迁移 KV Cache，还是重新 Prefill？
- 哪些专家需要提前部署到 B？
- 如何根据用户移动概率预测下一个服务节点？
- 如何在网络带宽有限时维持会话连续性？

研究核心：Joint Expert Placement and KV State Migration。

这个方向更偏 MobiCom / INFOCOM，网络和移动性特色更明显，但实现复杂度也更高。

备选方向 2

Thermal-aware Adaptive MoE Inference on Edge SoCs

研究场景：手机、Jetson、NPU 边缘设备。

现有系统通常根据预先测量的 CPU/GPU/NPU 执行延迟做调度。

但长时间运行时，设备可能发生 Thermal Throttling，CPU、GPU、NPU 的实际计算能力发生变化。

可以研究：

- 在线感知温度和 DVFS 状态。
- 动态调整 CPU/GPU/NPU Expert 执行位置。
- 动态调整 Prefetch 和 Batch Size。
- 在延迟 SLO 和能耗之间做优化。

研究核心：Hardware-state-aware MoE Scheduling。

这个方向更偏移动设备系统，可能适合 MobiCom，但需要有实际设备进行热特性测量。

## 四、最先做的实验应该是什么？

我认为这是整个计划最重要的一步。

实验主题：Expert Similarity 是否足以决定最佳 Batch？

设计一个非常简单的 2×2 对照实验。

|                 | 短上下文，例如 512 tokens | 长上下文，例如 8K tokens |
| --------------- | ------------------------- | ------------------------ |
| Expert 相似度高 | A                         | B                        |
| Expert 相似度低 | C                         | D                        |

其中 Expert Similarity 可以用各层激活专家集合的 Jaccard Similarity 进行初步衡量；更精细的指标可以采用 Saber 的 Activation Path Distance。

你需要验证的是：

当请求的 Expert Similarity 很高，但 Context Length 很长时，Saber 风格的分组收益是否可能被 KV Memory Pressure、Attention 开销或等待时间抵消？

这里有一个重要的实验控制：要保证不同方案处理的请求集合相同，严格记录它们的实际路由、总 Token 数和端到端延迟。 否则容易把长上下文本身更慢误判为调度问题。
